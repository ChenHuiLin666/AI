## 一、什么是 Skill

### 1.1 一句话定义

> **Skill 是一个可复用、可触发、打包好的 AI 指令集。** 它把"每次都要手写一遍的复杂指令"封装成"一个词就能触发的自动化流程"。

### 1.2 类比理解

| 类比 | 说明 |
|------|------|
| **函数之于代码** | `function deploy()` 封装了部署逻辑，Skill 就是 AI 的"函数" |
| **SOP 手册** | 公司里给新员工的标准化操作手册——遇到情况 X，按手册第 3 页的步骤执行 |
| **浏览器书签** | 把常用网址存为书签一键访问，Skill 把常用 AI 操作存为一键触发 |
| **Makefile** | `make build` 背后是一串命令，`/deploy` 背后是一串 AI 指令 |

### 1.3 为什么需要 Skill

没有 Skill 时的问题：

```
场景：每次部署都要告诉 AI 同样的步骤

第 1 次：
用户："帮我部署，先确认在 main 分支，跑一遍测试，
      构建 Docker 镜像，推送到 registry，
      然后更新 K8s deployment，最后验证健康检查通过..."
AI："好的，开始执行..."

第 10 次：
用户：（又要打一遍同样的指令...好烦）
```

有 Skill 之后：

```
用户："部署"
AI：（自动加载 deploy skill，按标准化流程执行）
```

**核心价值：把"经验"变成"系统能力"。**

## 二、Skill 的本质：Prompt 模板化

### 2.1 底层原理

Skill 的本质是一个**动态注入的 System Prompt 片段**：

```
用户触发 Skill
      │
      ▼
Claude Code 查找 Skill 文件
      │
      ▼
读取 Skill 的 Markdown 内容
      │
      ▼
将内容注入到当前对话的 System Prompt 中
      │
      ▼
AI 按照 Skill 中定义的规则、流程、约束来执行任务
```

### 2.2 运作方式

```
┌──────────────────────────────────────┐
│           System Prompt               │
│                                      │
│  ┌──────────────────────────────┐    │
│  │ 基础系统指令（角色、规则等）   │    │
│  └──────────────────────────────┘    │
│  ┌──────────────────────────────┐    │
│  │ Skill A 注入的指令            │    │  ← 用户触发 /deploy
│  │ "你是一个部署工程师..."        │    │
│  └──────────────────────────────┘    │
│  ┌──────────────────────────────┐    │
│  │ Skill B 注入的指令            │    │  ← 用户触发 /review
│  │ "你是一个代码审查专家..."      │    │
│  └──────────────────────────────┘    │
│                                      │
│  AI 综合所有指令来理解和执行任务      │
└──────────────────────────────────────┘
```

### 2.3 关键洞察

> **Skill 不是代码，是知识。** 它不执行任何逻辑，而是告诉 AI "在这种情况下，你应该这样思考、这样行动"。

这意味着：

- Skill 的内容是**自然语言指令**，不需要编程
- Skill 的效果取决于**指令的清晰度和完整度**
- Skill 可以包含**检查清单、决策树、代码规范、命名约定**等任何文字知识

## 三、Skill 的类型体系

### 3.1 按来源分类

```
Skills 来源层级（由外到内）：
┌─────────────────────────────────────┐
│  内置 Skills (Built-in)             │  ← Claude Code 自带
│  如 /review, /init, /simplify       │     优先级最低
├─────────────────────────────────────┤
│  插件 Skills (Plugin)               │  ← 第三方安装
│  如 plugin:dataviz, plugin:deploy   │
├─────────────────────────────────────┤
│  用户 Skills (User)                 │  ← 个人全局可用
│  ~/.claude/skills/                  │
├─────────────────────────────────────┤
│  项目 Skills (Project)              │  ← 当前项目可用
│  .claude/skills/                    │     优先级最高
└─────────────────────────────────────┘
```

同名 Skill 的优先级：项目级 > 用户级 > 插件 > 内置。

### 3.2 按功能分类

| 类型 | 说明 | 示例 |
|------|------|------|
| **流程类** | 标准化多步骤操作 | 部署流程、发布流程、onboarding |
| **规范类** | 代码风格、命名约定 | 组件命名规范、commit 格式 |
| **审查类** | 检查、验证、审计 | 代码审查、安全审查、性能审查 |
| **生成类** | 按模板生成内容 | 生成 CHANGELOG、生成 API 文档 |
| **转换类** | 格式/代码转换 | JS→TS 迁移、CSS→Tailwind 转换 |
| **学习类** | 引导学习某主题 | "教我理解这个代码库"、"解释这个架构" |

### 3.3 Skill 的两种运行模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **内联模式** | Skill 加载到当前对话，AI 直接执行 | 需要交互的流程（审查、重构） |
| **子 Agent 模式** | Skill 在独立 Agent 中执行，返回结果 | 独立任务（生成报告、批量处理） |

## 四、Skill 的触发机制

### 4.1 三种触发方式

#### 方式一：斜杠命令（显式触发）

```bash
/deploy           # 触发 deploy skill
/review           # 触发 review skill
/init             # 触发 init skill
```

用户主动调用，最直接的方式。

#### 方式二：自动匹配（隐式触发）

AI 根据用户意图自动判断应该加载哪个 Skill：

```
用户："帮我审查一下这些改动的代码"
AI：（自动识别 → 加载 code-review skill → 按审查清单逐项检查）
```

Skill 的 `description` 字段用于这个匹配过程——AI 读描述来判断是否匹配用户意图。

#### 方式三：项目指令触发

在 CLAUDE.md 或其他项目配置中指定默认加载的 Skill：

```markdown
# CLAUDE.md
本项目默认使用以下 Skills：
- code-style: 代码风格检查
- test-strategy: 测试策略
```

### 4.2 触发范围

```
触发 /deploy
      │
      ▼
查找 Skill "deploy"
      │
      ├── .claude/skills/deploy.md   ← 项目级，优先
      ├── ~/.claude/skills/deploy.md ← 用户级，备选
      ├── plugin:deploy              ← 插件级
      └── 内置 deploy               ← 内置级
      │
      ▼
加载第一个匹配到的 Skill
```

## 五、Skill 的文件结构

### 5.1 基本文件布局

```
.claude/skills/
├── deploy.md                # 部署 Skill
├── code-review.md           # 代码审查 Skill
├── release-notes.md         # 发布说明生成 Skill
└── test-strategy.md         # 测试策略 Skill
```

### 5.2 Skill 文件模板

```markdown
---
name: deploy
description: 按照标准流程部署项目到生产环境
type: workflow
---

# 部署流程

## 角色
你是一个资深的 DevOps 工程师，负责将项目安全可靠地部署到生产环境。

## 前置检查
在开始部署之前，你必须确认以下事项：

- [ ] 当前在 `main` 分支
- [ ] 工作区干净（没有未提交的改动）
- [ ] 所有 CI 测试通过
- [ ] 版本号已经更新（CHANGELOG.md 和 package.json）

如果任何一项不满足，拒绝部署并告知用户缺少什么。

## 部署步骤

### 1. 确认部署
向用户展示即将部署的版本和改动摘要，要求用户确认。

### 2. 构建
```bash
npm run build
```
确认构建成功，没有错误。

### 3. 测试
```bash
npm run test:e2e
```
如果测试失败，停止部署。

### 4. 发布
```bash
npm run release
```

### 5. 验证
部署完成后，执行健康检查：
```bash
curl -f https://your-app.com/health
```

### 6. 通知
告知用户部署完成，附带版本号和部署时间。

## 回滚方案
如果任何步骤失败：
1. 停止后续步骤
2. 告知用户失败原因和位置
3. 提供回滚命令：`npm run rollback`
```

### 5.3 Frontmatter 字段说明

```yaml
---
name: deploy                     # Skill 名称（触发词），kebab-case
description: 部署项目到生产      # 描述，用于自动匹配
type: workflow                   # 可选：workflow | reference | agent
trigger: manual                  # 可选：manual（手动）| auto（自动）
model: opus                      # 可选：指定使用的模型
---
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | Skill 的唯一标识，用作触发词 |
| `description` | 是 | 一句话描述，AI 用来自动匹配 |
| `type` | 否 | Skill 类型，影响加载和行为 |
| `trigger` | 否 | `manual`=仅斜杠触发，`auto`=AI 可自动加载 |
| `model` | 否 | 指定执行时使用的模型 |

### 5.4 内容区域的核心要素

一个好的 Skill 应该包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| **角色设定** | 赋予 AI 专业身份 | "你是一个资深代码审查专家" |
| **约束条件** | 不能做什么 | "不要修改测试文件" |
| **步骤流程** | 清晰的执行顺序 | 检查清单、步骤编号 |
| **判断标准** | 如何判断对错 | "代码复杂度 > 15 需要拆分" |
| **输出格式** | 规定输出结构 | "返回 Markdown 表格" |
| **异常处理** | 出错怎么办 | "如果测试失败，停止并告知" |

## 六、手写 Skill 全流程

### 6.1 第一步：识别可 Skill 化的任务

问自己三个问题：

```
Q1: 这个任务我做过 3 次以上了吗？
  → 是：值得做成 Skill

Q2: 这个任务有一套固定的步骤吗？
  → 是：适合做成 Skill

Q3: 别人也需要做这个任务吗？
  → 是：Skill 的复用价值更高
```

**适合做成 Skill 的信号**：

- 每次都要在 prompt 里写大段上下文说明
- 做这件事有固定的检查清单
- 新人常在这个任务上犯错
- 任务的执行标准可以被文档化

### 6.2 第二步：写出 Skill 初稿

从一个简单的 Markdown 文件开始：

```markdown
# 我的 Skill

## 你要做什么
...

## 怎么做
1. ...
2. ...
3. ...

## 注意事项
- ...
```

不要追求完美，先写一个能用的版本。

### 6.3 第三步：测试和迭代

```
1. 保存 Skill 文件到 .claude/skills/
2. 在 Claude Code 中用 /your-skill-name 触发
3. 观察 AI 的执行是否符合预期
4. 记录偏差 → 修改 Skill → 再次测试
5. 重复直到稳定
```

**迭代要点**：

- AI 跳过了一步？→ 加强约束语言（"你必须..."）
- AI 多做了一步？→ 加限制（"不要..."）
- 输出格式不对？→ 明确指定输出格式
- AI 理解有偏差？→ 加更具体的描述或示例

### 6.4 第四步：分享和维护

```
稳定后的 Skill →
  ├─ 提交到项目仓库（团队共享）
  ├─ 写使用文档
  ├─ 根据反馈持续改进
  └─ 版本号管理（重大变更时标注）
```

## 七、Skill vs 其他概念对比

### 7.1 Skill vs MCP Tool

这是最容易混淆的两个概念：

| 维度 | Skill | MCP Tool |
|------|-------|----------|
| **本质** | 指令/知识（告诉 AI 怎么做） | 函数/能力（让 AI 能做某件事） |
| **形式** | Markdown 文件 | 代码进程（TS/Python/Go...） |
| **执行者** | AI 自己 | 外部程序 |
| **触发** | 用户意图 → 加载指令 | AI 决策 → 调用函数 |
| **开发成本** | 低（写文档即可） | 中高（需要编程） |
| **灵活性** | 高（自然语言描述） | 低（受限于代码逻辑） |
| **确定性** | 低（依赖 AI 理解） | 高（代码逻辑确定） |

**一句话区分**：

> **Skill = 教 AI 怎么思考。MCP Tool = 给 AI 一个能做事的手。**

**配合使用**：

```
Skill "Bug 修复"
  ├─ 告诉 AI：先定位、再分析、再修复、最后测试
  └─ 使用 MCP Tool "jira_search" 来查询 Bug 信息
```

### 7.2 Skill vs Workflow

| 维度 | Skill | Workflow |
|------|-------|----------|
| **复杂度** | 简单，单一任务 | 复杂，多 Agent 编排 |
| **结构** | 线性 Markdown 文档 | JavaScript 脚本 + 编排逻辑 |
| **并发** | 不支持 | 支持 Pipeline/Parallel/Barrier |
| **验证** | 靠 AI 理解和指令约束 | 可编程验证、条件判断 |
| **适用** | 标准化操作流程 | 多维度分析、大规模处理 |

**关系**：

```
Skill 可以调用 Workflow：
  /audit → 加载 audit skill → skill 指示 AI 启动 audit-workflow

Workflow 可以引用 Skill：
  workflow 的某个步骤 → 调用 Agent → Agent 加载特定 Skill
```

### 7.3 Skill vs Agent

| 维度 | Skill | Agent |
|------|-------|-------|
| **自主性** | 被动加载，引导 AI | 主动规划，自主执行 |
| **工具使用** | 描述性指示 | 实际调用工具 |
| **决策能力** | 指令约束下的决策 | 目标驱动的自主决策 |
| **状态管理** | 无状态 | 有执行历史和中间状态 |

**关系**：

```
Skill 是 Agent 的"培训手册"
  Skill 告诉 Agent：在这种情况下你应该怎么做
  Agent 运用 Skill + 工具来完成目标
```

### 7.4 Skill vs Prompt

| 维度 | Skill | 普通 Prompt |
|------|-------|-------------|
| **复用性** | 一次编写，反复使用 | 每次手写 |
| **可分享** | 文件形式，团队共享 | 复制粘贴文本 |
| **可发现** | AI 自动匹配加载 | 需要用户记得写 |
| **版本管理** | Git 跟踪 | 无版本管理 |
| **结构化** | 有 frontmatter + 规范 | 自由格式 |

> **Skill 是沉淀下来的 Prompt。** 当你发现某个 prompt 反复写、效果稳定时，就是把它升级为 Skill 的时候。

## 八、Skill 设计原则与最佳实践

### 8.1 设计原则

#### 原则一：单一职责

```
❌ 差：一个 Skill 既做代码审查又做部署又写文档
✅ 好：三个独立 Skill：code-review、deploy、generate-docs
```

一个 Skill 只解决一个问题。多个小 Skill 可以组合。

#### 原则二：显式优于隐式

```
❌ 隐式: "按照规范处理"          → AI 不知道规范是什么
✅ 显式: "使用 ESLint 规则检查，忽略 any 类型的 warning"
```

不要假设 AI 知道你的上下文。把约束写清楚。

#### 原则三：包含判断标准

```
❌ 模糊: "检查代码质量"
✅ 明确: "检查代码质量，以下任一条件不满足即不合格：
  - 圈复杂度 > 10
  - 函数超过 50 行
  - 缺少类型注解"
```

AI 需要明确的"对/错"标准。

#### 原则四：提供输出格式

```
❌ 无格式: "告诉我结果"
✅ 有格式: "输出 JSON：
  {
    passed: boolean,
    issues: [{ file: string, line: number, message: string, severity: 'error'|'warn' }],
    summary: string
  }"
```

明确的输出格式让结果可解析、可对比。

#### 原则五：渐进式完善

```
v1.0: 写基本步骤，能用就行
v1.1: 加一些约束，修复偏差
v1.2: 加输出格式，规范化
v2.0: 加检查清单、异常处理、示例
```

不要试图一开始就完美。

### 8.2 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 指令过于简短 | AI 理解偏差大 | 写完整段落，不要只写关键词 |
| 没有角色设定 | AI 行为不稳定 | 加一句"你是一个...专家" |
| 缺少异常处理 | 遇到错误就卡住 | 写明"If X fails, do Y" |
| 步骤之间有关联但没说 | AI 可能乱序执行 | 明确标注依赖关系 |
| 内容过长 | 占用太多 token | 拆分多个 Skill，SKILL_A 调用 SKILL_B |
| 只有"怎么做"没有"为什么" | AI 在边界情况瞎猜 | 解释设计意图 |

## 九、高级模式

### 9.1 链式 Skill

一个 Skill 的执行结果触发另一个 Skill：

```markdown
# code-review skill

## 完成审查后
如果发现需要重构的问题，建议用户运行：
/review-to-refactor
```

### 9.2 条件分支 Skill

在 Skill 中嵌入决策逻辑：

```markdown
## 判断分支

### 如果是前端项目
- 检查组件命名（PascalCase）
- 检查是否有 PropTypes/类型定义
- 运行 `npm run lint`

### 如果是后端项目
- 检查 API 端点是否有文档
- 检查错误处理是否完整
- 运行 `npm run test:unit`
```

### 9.3 带参数的 Skill

```markdown
---
name: generate-changelog
description: 生成版本发布说明
---

## 参数
- version: 版本号（如 v1.2.0）
- from: 起始 commit/tag
- to: 结束 commit/tag

## 步骤
1. 获取 {from} 到 {to} 之间的所有 commit
2. 分类：Features / Fixes / Breaking Changes / Docs
3. 按以下格式输出：
  # {version} ({date})
  ## Features
  - ...
  ## Fixes
  - ...
```

### 9.4 自我验证 Skill

Skill 执行完后自动验证自己的输出：

```markdown
## 完成后自我检查
在交付结果之前，确认：
1. 所有检查项都已覆盖
2. 没有误报（每个 issue 都是真实存在的）
3. 严重程度分级合理
4. 每个 issue 有明确的文件路径和行号

如果不满足，修正后再交付。
```

### 9.5 Skill 组合模式

```
用户: "帮我做一次完整的发布"

AI: （加载 release skill）
    ├── 步骤 1: 触发 changelog skill → 生成 CHANGELOG
    ├── 步骤 2: 触发 code-review skill → 最终审查
    ├── 步骤 3: 触发 deploy skill → 部署
    └── 步骤 4: 触发 release-notes skill → 发布公告
```

## 十、实战案例

### 10.1 案例一：代码审查 Skill

```markdown
---
name: code-review
description: 按照团队规范审查代码改动，检查正确性、安全性、可维护性
---

# 代码审查

## 角色
你是一个资深软件工程师，以严谨但友好的方式审查代码。

## 审查维度（按优先级）

### 1. 正确性（最高优先级）
- 逻辑是否正确？边界情况是否处理？
- 空值、异常、并发竞态是否考虑？
- 类型使用是否正确？

### 2. 安全性
- 是否有注入风险（SQL、XSS 等）？
- 敏感信息是否暴露？
- 权限校验是否完整？

### 3. 可维护性
- 命名是否清晰表达意图？
- 函数是否单一职责？
- 是否有不必要的复杂度？
- 注释是否解释了"为什么"而非"做了什么"？

### 4. 性能
- 是否有不必要的循环或重复计算？
- 数据库查询是否有 N+1 问题？
- 是否有内存泄漏风险？

## 输出格式
对于每个发现的问题，按以下格式输出：

| 严重度 | 文件:行号 | 问题 | 建议 |
|--------|----------|------|------|

严重度：🔴 必须修改 | 🟡 建议修改 | 🟢 可选优化

## 审查原则
- 对事不对人
- 每个建议都要给出理由
- 如果代码没问题，直接说 LGTM
- 不要对同一问题重复评论
```

### 10.2 案例二：API 设计审查 Skill

```markdown
---
name: api-review
description: 审查 REST API 设计是否符合团队规范
---

# API 设计审查

## 角色
你是一个 API 设计专家，精通 RESTful 规范和团队内部标准。

## 检查清单

### URL 设计
- [ ] 使用复数名词（/users 而非 /user）
- [ ] 资源嵌套不超过 2 层
- [ ] 使用 kebab-case（/user-orders 而非 /userOrders）
- [ ] 版本号在 URL 中（/api/v1/...）

### HTTP 方法
- [ ] GET 只读，不修改资源
- [ ] POST 创建新资源
- [ ] PUT 完整替换，PATCH 部分更新
- [ ] DELETE 幂等（多次调用结果一致）

### 响应
- [ ] 使用正确的 HTTP 状态码
- [ ] 错误响应包含 code、message、details
- [ ] 列表接口支持分页（page、page_size）
- [ ] 时间字段使用 ISO 8601 格式

### 安全
- [ ] 敏感接口有权限控制
- [ ] 输入参数有校验
- [ ] 响应不泄露内部信息（栈追踪等）

## 输出格式
审查结果为 JSON：
{
  "score": "pass|fail|warn",
  "issues": [...],
  "suggestions": [...]
}
```

### 10.3 案例三：Git Commit 规范 Skill

```markdown
---
name: commit
description: 生成符合 Conventional Commits 规范的 commit message
---

# 生成 Commit Message

## 规范
遵循 Conventional Commits 规范：
<type>(<scope>): <subject>

## 类型判断
根据改动内容自动判断 type：
- feat: 新功能
- fix: Bug 修复
- refactor: 重构（不改变功能）
- perf: 性能优化
- style: 代码格式（不影响逻辑）
- docs: 文档变更
- test: 测试相关
- chore: 构建/工具变更

## Subject 规则
- 使用中文
- 不超过 50 字符
- 以动词开头（"添加"而非"添加了"）
- 描述改动本身，而非改动的原因

## 流程
1. 分析当前暂存区的改动
2. 判断属于什么类型
3. 生成 3 个候选 message
4. 让用户选择或编辑
5. 执行 git commit
```

## 十一、总结

### Skills 的核心思想

```
日常工作中反复做的事 → 抽象为标准流程 → 写成 Markdown 文件 → AI 自动按流程执行
```

### Skills 的三层价值

| 层次 | 价值 | 说明 |
|------|------|------|
| **个人效率** | 不用反复写同样的 prompt | 一次编写，终身复用 |
| **团队标准化** | 所有人用同样的流程 | 代码审查标准、部署流程统一 |
| **知识沉淀** | 把经验固化到系统中 | 人走了，Skill 还在 |

### Skill 开发的心智模型

```
Skill 开发 ≠ 编程
Skill 开发 = 写一份好的 SOP（标准操作流程）

你的用户是 AI：
  - 它很聪明，但需要明确的指导
  - 它不会"理解弦外之音"，所有约束要显式写出
  - 它需要判断标准，而不是模糊的方向
```

### 从入门到精通的路径

```
Level 1: 使用内置 Skills
  → 理解 Skill 能做什么

Level 2: 写第一个简单 Skill
  → 把常做的事写成一个 Skill 文件

Level 3: 为团队建立 Skill 库
  → 标准化代码审查、部署、文档生成等流程

Level 4: 设计 Skill 体系
  → Skill 之间互相引用、组合，形成完整的 AI 工作体系

Level 5: 贡献到社区
  → 把通用 Skill 开源，帮助更多人
```

### 最后的话

> **Skill 是 AI 时代的"最佳实践文档"——只不过这份文档的读者不只有人类，还有 AI。**
>
> 写好 Skill 的本质，是把你脑子里的隐性知识转化为 AI 能理解和执行的结构化指令。
> 这个过程本身，就是在把你的专业能力系统化、可复制化。
